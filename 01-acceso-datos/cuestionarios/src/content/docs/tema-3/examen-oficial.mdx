## 3. Uso de PreparedStatement

¿Para qué se usa la interfaz `PreparedStatement`?

- **a.** Se utiliza para implementar sentencias SQL simples sin parámetros.
  > Puede ejecutar SQL sin parámetros, pero eso no caracteriza a `PreparedStatement`; también puede hacerlo un `Statement`.
- **b.** Se utiliza para compilar previamente sentencias SQL que pueden contener parámetros de entrada. <Badge text="Correcta" variant="success" />
  > Es la interfaz para sentencias preparadas. Permite vincular los valores de los marcadores `?` y ejecutar la sentencia más de una vez.
- **c.** Todas las demás respuestas son correctas.
  > La opción que describe los parámetros de salida corresponde a `CallableStatement`.
- **d.** Se utiliza para ejecutar procedimientos almacenados que pueden contener parámetros de entrada y salida.
  > JDBC ofrece `CallableStatement` para estas llamadas y para registrar parámetros de salida.

Repasar: 3A §5 y §8.

## 4. Sentencias preparadas e inyección SQL

Las sentencias preparadas evitan la inyección SQL. ¿Es correcto?

- **a.** Incorrecto.
  > Usadas con parámetros, sí protegen los valores vinculados como datos.
- **b.** Ninguna de las otras respuestas es correcta.
  > «Correcto» es la respuesta cuando los datos de entrada se vinculan como parámetros.
- **c.** Las sentencias preparadas no tienen nada que ver con la inyección SQL.
  > La separación entre sintaxis SQL y valores es precisamente lo que aporta la protección.
- **d.** Correcto. <Badge text="Correcta" variant="success" />
  > Los valores vinculados a `?` no se interpretan como código SQL. Crear un `PreparedStatement` no protege fragmentos de SQL que se hayan construido concatenando entradas.

## 6. Estándares ODBC y JDBC

Indica cuál de las siguientes afirmaciones es **falsa** en relación con los estándares de conectividad ODBC y JDBC.

- **a.** JDBC es un estándar de conexión adaptado a las especificidades de Java.

- **b.** ODBC se puede conectar a distintos tipos de sistemas de gestión de bases de datos, aunque no sean de Microsoft.
  > Es verdadera: ODBC puede utilizarse con distintos fabricantes si existe un controlador compatible.
- **c.** Para ODBC no hace falta que las empresas desarrolladoras de sistemas de gestión de bases de datos desarrollen controladores de conexión; fue el gran avance que trajo ODBC al mercado. <Badge text="Correcta" variant="success" />
  > Es la afirmación falsa en el sentido del examen: una interfaz común no elimina la necesidad de un controlador compatible con el motor. Puede suministrarlo el fabricante o un tercero.
- **d.** Ambos son estándares de interfaz que permiten a las aplicaciones conectarse a diferentes sistemas de gestión de bases de datos.
  > Es verdadera: ambos ofrecen una interfaz común sobre controladores específicos.

## 7. Procedimientos y funciones

¿Qué interfaz se utiliza en JDBC para invocar procedimientos y funciones almacenados en la base de datos y a través de qué método de `Connection` se crea?

- **a.** `PreparedStatement`, mediante `prepareStatement()`.
  > Prepara SQL con parámetros de entrada. La interfaz que JDBC dedica a las llamadas a rutinas es `CallableStatement`.
- **b.** `CallableStatement`, mediante `prepareCall()`. <Badge text="Correcta" variant="success" />
  > `Connection.prepareCall(...)` devuelve un `CallableStatement`, que admite el registro de parámetros de salida.
- **c.** `DatabaseMetaData`, mediante `getMetaData()`.
  > Permite consultar información sobre la base de datos, el controlador y sus capacidades.
- **d.** `Statement`, mediante `createStatement()`.
  > Crea una sentencia general. No proporciona la API de `CallableStatement` para parámetros de salida.

Repasar: 3A §8, procedimientos almacenados.

## 9. Información de una URL JDBC

La cadena de conexión es `String url = "jdbc:mysql://localhost:3306/world";`. Señala qué **no** dice este parámetro sobre la conexión.

- **a.** El servidor está en el mismo host que el programa Java.
  > `localhost` indica que el programa intenta conectarse al host local.
- **b.** La base de datos está levantada para recibir peticiones. <Badge text="Correcta" variant="success" />
  > La URL describe el destino, pero no indica si está disponible. Eso se comprueba al intentar conectarse.
- **c.** El nombre de la base de datos de conexión.
  > El segmento `/world` indica el nombre de la base de datos solicitada.
- **d.** El servidor está en el puerto `3306`.
  > `:3306` indica el puerto de destino, aunque no garantiza que haya un servidor escuchando.

Repasar: 3A §3, URL de conexión.

## 10. Cursor desplazable sensible

Al configurar un `ResultSet`, ¿qué tipo de cursor permite desplazarse tanto hacia delante como hacia atrás y refleja además en tiempo real las modificaciones realizadas por otras transacciones concurrentes?

- **a.** `ResultSet.TYPE_SCROLL_INSENSITIVE`.
  > Permite desplazarse en ambos sentidos, pero normalmente no refleja los cambios de los datos subyacentes.
- **b.** `ResultSet.TYPE_SCROLL_SENSITIVE`. <Badge text="Correcta" variant="success" />
  > Es la opción esperada: permite desplazarse en ambos sentidos y suele ser sensible a cambios en los datos. «En tiempo real» no es una garantía universal; la visibilidad depende del controlador, el motor y el aislamiento.
- **c.** `ResultSet.CONCUR_UPDATABLE`.
  > Es un modo de concurrencia para modificar filas a través del resultado; no determina cómo puede desplazarse el cursor.
- **d.** `ResultSet.TYPE_FORWARD_ONLY`.
  > Solo permite desplazarse hacia delante.

Repasar: 3A §10, tipo y concurrencia.

## 11. Controlador JDBC de tipo 1

¿Cómo se denominan y cuál es el funcionamiento principal de los conectores JDBC de tipo 1?

- **a.** Son controladores 100 % Java puro que se comunican directamente con el protocolo propietario de la base de datos.

- **b.** Se conocen como API nativa y traducen las llamadas JDBC directamente a código nativo de la máquina cliente sin pasar por ODBC.

  > El puente delega el acceso al gestor en la capa ODBC y su controlador.
- **d.** Son controladores de red en Java puro que envían las peticiones a un servidor intermedio o middleware.
  > Esa es la descripción del tipo 3.

## 12. Rendimiento de las sentencias preparadas

Una sentencia preparada es más lenta que una sentencia SQL no preparada. ¿Es correcto?

- **a.** Sí, al ser precompilada tarda más en ser ejecutada.
  > Preparar tiene un coste inicial, pero dicho coste puede amortizarse si se reutiliza la misma sentencia.
- **b.** No, son iguales.
  > No hay una igualdad de rendimiento garantizada entre las dos formas de ejecución.
- **c.** Ninguna de las otras respuestas es correcta.
  > Una lectura estricta admite esta opción, porque ninguna comparación absoluta se cumple siempre. En el contexto del temario, se espera reconocer la ventaja al reutilizar la preparación.
- **d.** No, es más rápida. <Badge text="Respuesta esperada" variant="success" />
  > Es la respuesta esperada según el temario: al repetir la consulta con distintos parámetros se puede ahorrar trabajo de preparación. Una ejecución aislada no tiene por qué ser más rápida; depende del motor y del controlador.

## 19. Sentencias que admite JDBC

¿Qué tipos de sentencias se pueden ejecutar con JDBC?

- **a.** Consultas.
  > Sí, por ejemplo `SELECT` con `executeQuery()`; también se admiten DDL y DML.
- **b.** Sentencias DDL.
  > Sí, por ejemplo `CREATE TABLE` con `executeUpdate()`; no es la única categoría.
- **c.** Todas las otras respuestas son correctas. <Badge text="Correcta" variant="success" />
  > JDBC puede ejecutar consultas, sentencias DDL que cambian el esquema y sentencias DML que modifican los datos.
- **d.** Sentencias DML.
  > Sí, por ejemplo `INSERT`, `UPDATE` y `DELETE` con `executeUpdate()`; también se admiten consultas y DDL.

## 20. Almacenamiento de lecturas sin conexión

Un dispositivo que monitoriza el clima tiene pocos recursos de hardware y necesita guardar lecturas cada cierto tiempo. Algunos dispositivos tienen conexión a Internet, otros no, y algunas conexiones se pierden temporalmente. ¿Qué tipo de base de datos es más adecuado?

- **a.** Ambas soluciones son adecuadas.
  > Un servidor local en el propio dispositivo puede funcionar sin Internet, pero añade el coste de mantener otro proceso. Con pocos recursos, la opción embebida encaja mejor.
- **b.** Optaría por una base de datos cliente-servidor en local.
  > Puede funcionar sin Internet si el servidor es accesible localmente, pero requiere desplegar y mantener un servidor separado de la aplicación.
- **c.** Ninguna solución es adecuada.
  > Una base embebida sí cubre la necesidad de escribir lecturas localmente con poca infraestructura.
- **d.** Optaría por una base de datos embebida. <Badge text="Correcta" variant="success" />
  > Por ejemplo, SQLite guarda las lecturas en un fichero local sin un proceso servidor independiente y sin depender de Internet.

Repasar: 3B §1 y §2, base embebida frente a cliente-servidor.
